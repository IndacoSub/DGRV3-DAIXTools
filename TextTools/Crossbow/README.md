# TEXTTOOLS - CROSSBOW
## Team DAIX, 2026  

---

## 📌 Overview

**Crossbow** is the TextTools component responsible for the **final distribution of modified game resources**.

Its purpose is to take the SPC/PB files produced or modified by the preceding TextTools pipeline, determine which ones actually need to be distributed, and copy only those files into the appropriate output structure.

Rather than copying the entire:

```text
DGRV3/base_spc/
````

directory, Crossbow uses:

```text
different_hashes.txt
```

generated by **Necronomicon** to determine which chapters contain modified resources.

This makes Crossbow an **incremental distribution stage**.

Its normal operation is:

```text
Necronomicon
      │
      ▼
different_hashes.txt
      │
      ▼
Crossbow
      │
      ├── determine modified chapters
      ├── find matching SPC/PB files
      ├── map them to distribution folders
      └── copy them
             │
             ▼
       ModifiedFiles/
```

Crossbow also has a second operating mode, **Part 2**, which uses different input/output rules and handles special French trial resources.

---

# 🎯 Responsibilities

Crossbow performs several distinct tasks:

### ✔ 1. Read modification information

It reads:

```text
different_hashes.txt
```

and extracts the chapter/folder names associated with changed files.

---

### ✔ 2. Find modified SPC/PB resources

It scans the appropriate source directory and selects:

* modified `.SPC` files,
* modified `.PB` files,
* and, in Part 2 mode, explicitly selected French trial SPC files.

---

### ✔ 3. Map resources to their distribution directories

SPC files are categorized into:

```text
game_resident/
wrd_data/
wrd_script/007/
```

while PB files are placed into:

```text
master/
```

---

### ✔ 4. Handle special trial resources

Crossbow has dedicated handling for:

```text
hanron
nonstop
panic
kokoronpa
nico
```

trial files.

These receive special treatment in Part 2 mode.

---

### ✔ 5. Rename French trial files

In Part 2 mode, French trial files such as:

```text
hanron_01_FR.spc
```

are distributed under the corresponding US name:

```text
hanron_01_US.spc
```

---

### ✔ 6. Record copied files

Crossbow appends the processed file paths to:

```text
file_copied.txt
```

---

### ✔ 7. Clean Part 2 distribution leftovers

When operating in Part 2 mode, Crossbow removes leftover files from:

```text
Distribute/
```

so that the resulting distribution directory contains only the intended files.

---

# 🧩 How Crossbow Fits Into TextTools

Crossbow is the **distribution stage** at the end of the pipeline.

A simplified pipeline is:

```text
Ropeway
   ↓
CrammedPiranhas
   ↓
MarkerStone
   ↓
Necronomicon
   ↓
Bugvac
   ↓
HydraulicPress
   ↓
PoolRules
   ↓
ElectroHammer
   ↓
Crossbow
```

The important distinction is:

```text
ElectroHammer
    ↓
builds/modifies SPC resources

Crossbow
    ↓
selects and distributes those resources
```

ElectroHammer produces the game resources.

Crossbow determines which resulting resources need to be packaged, tested, or shipped.

---

# 🔗 Relationship With Necronomicon

Crossbow relies directly on:

```text
different_hashes.txt
```

This file is produced by **Necronomicon**.

The relationship is:

```text
Necronomicon
      │
      │ detects changed scripts/resources
      ▼
different_hashes.txt
      │
      ▼
Crossbow
      │
      │ determines affected chapters
      ▼
Modified SPC/PB files
```

Crossbow does **not** calculate hashes itself.

Instead, it uses Necronomicon's results as its change-detection input.

---

# 📄 `different_hashes.txt`

Crossbow reads this file at startup:

```text
different_hashes.txt
```

It processes every line and searches it for recognized chapter names.

For example, if the file contains a path associated with:

```text
chapter3
```

Crossbow records:

```text
chapter3
```

in its internal `logged` list.

---

# 🧠 Important: Crossbow Does Not Store Filenames

Although the file is called:

```text
different_hashes.txt
```

Crossbow does not preserve the individual changed filenames.

Instead, `LoadLoggedFromFile()` extracts only the recognized **chapter/folder name**.

For example:

```text
DGRV3/chapter3/scene_12.txt
```

becomes:

```text
chapter3
```

in the `logged` vector.

Therefore Crossbow operates at a **chapter/resource-group level**, not at an individual script-file level.

---

# 📂 Recognized Chapter Mappings

Crossbow defines the following mappings:

| SPC Prefix          | Chapter / Folder |
| ------------------- | ---------------- |
| `chap0`             | `prologue`       |
| `chap1`             | `chapter1`       |
| `chap2`             | `chapter2`       |
| `chap3`             | `chapter3`       |
| `chap4`             | `chapter4`       |
| `chap5`             | `chapter5`       |
| `chap6`             | `chapter6`       |
| `chap7`             | `epilogue`       |
| `map_obj_name_text` | `MapObjName`     |
| `game_resident`     | `game_resident`  |
| `gallery`           | `gallery`        |
| `ainori`            | `ainori`         |

These mappings are stored in the `chapters` vector.

---

# ⚠️ Important Chapter Coverage Limitation

The chapter mapping does **not** include every TextTools folder.

For example:

```text
test
subroutine
```

do not appear in Crossbow's `chapters` mapping.

Therefore, Crossbow cannot automatically associate those resources with a `logged` chapter through `LoadLoggedFromFile()`.

This is an important difference from tools such as ElectroHammer, which explicitly recognize all 14 TextTools folders.

---

# 🧾 The `logged` Vector

Crossbow stores recognized modified chapters in:

```cpp
std::vector<std::string> logged;
```

For example:

```text
logged:
    chapter1
    chapter3
    game_resident
```

This list becomes the basis for determining which SPC files should be copied.

---

# 🔎 `LoadLoggedFromFile()`

`LoadLoggedFromFile()` performs the following operations:

1. Opens `different_hashes.txt`.
2. Reads it line by line.
3. Checks every line against the known chapter names.
4. Adds matching chapter names to `logged`.
5. Prevents duplicate chapter names.
6. Logs the resulting chapter list.

Conceptually:

```text
different_hashes.txt
        │
        ▼
read line
        │
        ▼
check all known mappings
        │
        ▼
recognized chapter?
        │
        ├── yes → add to logged
        │
        └── no  → ignore
```

---

# ⚠️ Missing `different_hashes.txt`

If Crossbow cannot open:

```text
different_hashes.txt
```

it prints:

```text
Error: Could not open different_hashes.txt
```

and continues execution.

It does **not** immediately terminate.

As a result, `logged` may remain empty, which can cause normal SPC files to be skipped.

PB files remain eligible because PB files are always selected.

---

# 🔨 `ShouldBeSaved()`

`ShouldBeSaved()` determines whether an SPC filename belongs to one of the chapters recorded in `logged`.

It compares the filename against the prefix mappings.

For example:

```text
chap3_text_US.SPC
```

contains:

```text
chap3
```

so it corresponds to:

```text
chapter3
```

If `chapter3` is in `logged`, the function returns:

```text
true
```

---

# ⚠️ `ShouldBeSaved()` Consumes Chapter Entries

One of the most important quirks in Crossbow is that `ShouldBeSaved()` **removes the matching chapter from `logged` once it is used**.

Conceptually:

```text
logged:
    chapter1
    chapter3

process chap1_text_US.SPC
        ↓
chapter1 matched
        ↓
remove chapter1

logged:
    chapter3
```

This means a logged chapter is effectively a **one-time selection token**.

---

# 🚨 Consequence of One-Time Consumption

Because `ShouldBeSaved()` removes a chapter after the first match, Crossbow does not simply mean:

> "copy every file belonging to every changed chapter."

Instead, the current implementation effectively means:

> "the first matching SPC filename for a logged chapter is selected."

For normal chapter SPC naming, this may be exactly what the tool expects because each chapter corresponds to a single principal SPC archive.

However, developers should be aware that this is not a general-purpose multi-file chapter matcher.

---

# 📁 Normal Mode

Normal Crossbow operation uses:

```text
ModifiedFiles/
```

as the output directory.

The source directory is:

```text
DGRV3/base_spc/
```

Therefore:

```text
DGRV3/base_spc/
        │
        ▼
    Crossbow
        │
        ▼
ModifiedFiles/
```

---

# 🟢 Normal Mode Command

Normal mode is simply:

```text
Crossbow.exe
```

with no:

```text
part2
```

argument.

---

# 📂 Normal Mode Source

The source directory is:

```text
DGRV3/base_spc/
```

Crossbow recursively scans this directory.

It considers only:

```text
.spc
.pb
```

files.

---

# 📂 Normal Mode Destination

The initial distribution directory is:

```text
ModifiedFiles/
```

Crossbow then creates subdirectories based on the type of resource.

---

# 🗂️ Normal Distribution Layout

The resulting structure is conceptually:

```text
ModifiedFiles/
├── game_resident/
│   └── *.spc
│
├── wrd_data/
│   ├── map_obj_name_text_*.spc
│   └── trial files
│
├── wrd_script/
│   └── 007/
│       └── chapter SPC files
│
└── master/
    └── *.pb
```

---

# 🏠 `game_resident/`

Any SPC filename containing:

```text
game_resident
```

is placed into:

```text
ModifiedFiles/game_resident/
```

Example:

```text
game_resident_US.spc
```

becomes:

```text
ModifiedFiles/game_resident/game_resident_US.spc
```

---

# 🗺️ `wrd_data/`

SPC files containing:

```text
map_obj_name_text
```

are placed into:

```text
ModifiedFiles/wrd_data/
```

Trial SPC files are also classified into this directory.

---

# 📜 `wrd_script/007/`

All other SPC files that are not:

```text
game_resident
```

or:

```text
map_obj_name_text
```

or trial files

are placed under:

```text
ModifiedFiles/wrd_script/007/
```

The game revision is hardcoded as:

```cpp
latest_game_revision = "007";
```

Therefore the destination is currently:

```text
wrd_script/007/
```

---

# ⚠️ Hardcoded Game Revision

The value:

```text
007
```

is hardcoded.

Changing the target game revision requires a source modification.

It is not read from a configuration file or command-line argument.

---

# 📦 PB Files

PB files are handled differently from SPC files.

A PB file is considered modified **regardless of whether its chapter is listed in `logged`**.

The selection condition is effectively:

```text
modified =
    ShouldBeSaved(filename)
    OR
    extension == ".pb"
```

Therefore:

```text
PB files → always copied
```

in the scan.

---

# 📁 PB Destination

PB files are placed into:

```text
master/
```

Thus normal mode produces:

```text
ModifiedFiles/master/<file>.pb
```

---

# 🔍 File Extension Handling

Crossbow converts the file extension to lowercase before testing it.

Therefore:

```text
.SPC
.spc
.SpC
```

are all recognized as SPC files.

Likewise, uppercase variants of PB are recognized by the extension check.

---

# 🚫 Ignored File Types

Crossbow ignores anything that is not:

```text
.spc
.pb
```

For example:

```text
.txt
.stx
.srdv
.json
```

are ignored.

It logs ignored files to the console.

---

# 🚫 `_extracted` Directories

Crossbow skips files whose path contains:

```text
_extracted
```

These are treated as temporary extraction outputs rather than final distributable SPC/PB resources.

This prevents extracted intermediate data from being distributed accidentally.

---

# 🔄 Recursive Scanning

Crossbow uses:

```text
std::filesystem::recursive_directory_iterator
```

to scan the selected source directory.

In normal mode, this means nested directories are traversed.

---

# 🧭 Part 2 Mode

Crossbow has a second operating mode activated with:

```text
part2
```

The argument can appear as either:

```text
Crossbow.exe part2
```

or:

```text
Crossbow.exe <anything> part2
```

The implementation checks both the first and second command-line arguments.

---

# 🟣 Part 2 Purpose

Part 2 changes several aspects of Crossbow:

```text
Source directory
Output directory
Trial handling
FR → US renaming
Cleanup behavior
```

The high-level flow becomes:

```text
Distribute/
    │
    ▼
Crossbow Part2
    │
    ├── scan top-level SPC/PB files
    ├── add special FR trial files
    ├── copy distribution files
    ├── rename FR trials to US
    └── remove leftovers
```

---

# 📂 Part 2 Source Directory

Unlike normal mode, Part 2 scans:

```text
Distribute/
```

rather than:

```text
DGRV3/base_spc/
```

The source directory is selected with:

```cpp
auto dir = part2 ? actualdist : where;
```

where:

```text
actualdist = Distribute/
where      = DGRV3/base_spc/
```

---

# ⚠️ Part 2 Scanning Depth

Part 2 only scans the top level of:

```text
Distribute/
```

When the iterator enters a subdirectory, recursion is disabled.

Therefore:

```text
Distribute/file.spc
```

is considered.

But:

```text
Distribute/subfolder/file.spc
```

is not recursively scanned.

This is an important difference from normal mode.

---

# 📁 Part 2 Destination

Normal files are copied into:

```text
Distribute/<mapped folder>/
```

while trial files are ultimately placed into:

```text
ModifiedFiles/wrd_data/
```

with their names converted from FR to US.

This means Part 2 has an unusual split:

```text
Normal Part 2 resources
    → Distribute/

Trial Part 2 resources
    → ModifiedFiles/wrd_data/
```

---

# 🧪 Special Trial Files

Part 2 explicitly adds the following French trial resources:

```text
hanron_01_FR.spc
hanron_02_FR.spc
hanron_03_FR.spc
hanron_04_FR.spc
hanron_05_FR.spc
hanron_06_FR.spc

kokoronpa_08_FR.spc

nico_06_FR.spc

nonstop_01_FR.spc
nonstop_02_FR.spc
nonstop_03_FR.spc
nonstop_04_FR.spc
nonstop_05_FR.spc
nonstop_06_FR.spc

panic_01_FR.spc
panic_02_FR.spc
panic_03_FR.spc
panic_04_FR.spc
panic_05_FR.spc
panic_06_FR.spc
```

These are manually appended to the `modified` list.

They are therefore distributed regardless of whether `different_hashes.txt` contains their corresponding chapter.

---

# 📂 Trial Source Location

The trial resources are expected under:

```text
DGRV3/base_spc/trial_french_extracted/
```

For example:

```text
DGRV3/base_spc/trial_french_extracted/hanron_01_FR.spc
```

---

# ⚠️ Trial Files Are Always Added in Part 2

The trial files are explicitly pushed into the `modified` vector.

Therefore Part 2 treats them as mandatory distribution inputs.

If one of the expected files does not exist, the later copy stage logs:

```text
File does not exist
```

and continues.

---

# 🇫🇷 French Trial Files

Crossbow recognizes trial resources through names such as:

```text
hanron_
kokoronpa_08_
nico_06_
nonstop_
panic_
```

A file containing one of these patterns is considered a trial SPC.

---

# 🚫 Non-FR Trial Files

Crossbow contains an additional rule:

```text
if trial file && filename does not contain "_FR"
    skip
```

Therefore, trial files that are not French are ignored during distribution.

---

# 🔄 FR → US Renaming

In Part 2 mode, a French trial file:

```text
nonstop_01_FR.spc
```

is renamed to:

```text
nonstop_01_US.spc
```

The replacement is performed using:

```text
std::regex_replace(
    file_name,
    std::regex("FR"),
    "US"
)
```

---

# ⚠️ FR Replacement Is Regex-Based

The replacement is not specifically restricted to the filename suffix.

The regular expression is simply:

```text
FR
```

Therefore every occurrence of the literal sequence:

```text
FR
```

in the filename is replaced with:

```text
US
```

For the intended trial filenames, this produces the expected:

```text
_FR → _US
```

conversion.

---

# 🗺️ Trial Destination

Trial files are classified as:

```text
wrd_data
```

They are therefore intended for:

```text
ModifiedFiles/wrd_data/
```

in Part 2.

---

# 🧠 Resource Classification Logic

For every selected file, Crossbow determines its destination using the following conceptual logic:

```text
Is it an SPC?
        │
        ├── yes
        │    │
        │    ├── game_resident?
        │    │       └── game_resident/
        │    │
        │    ├── map_obj_name_text?
        │    │       └── wrd_data/
        │    │
        │    ├── trial file?
        │    │       └── wrd_data/
        │    │
        │    └── otherwise
        │            └── wrd_script/007/
        │
        └── no
             │
             └── PB
                  ↓
                master/
```

---

# 📋 Selection vs Classification

Crossbow separates two different decisions.

### Selection

Determines:

> Should this file be copied at all?

Based on:

```text
logged chapters
PB status
Part 2 trial rules
```

### Classification

Determines:

> Where should this file be copied?

Based on:

```text
SPC/PB type
filename patterns
trial status
game revision
```

This distinction is important when debugging the tool.

---

# 📦 Copy Operation

After building the `modified` list, Crossbow iterates over every selected file.

For each file it:

1. validates the path,
2. determines whether it is a trial,
3. determines the destination category,
4. creates destination directories,
5. copies the file,
6. records success/failure.

---

# 🗂️ Destination Directory Creation

Crossbow calls:

```text
std::filesystem::create_directories(dest.parent_path());
```

Therefore the expected output hierarchy is created automatically.

Developers do not need to manually create:

```text
wrd_data/
wrd_script/007/
game_resident/
master/
```

before running the tool.

---

# 🔁 Overwriting Existing Files

The normal C++20 implementation uses:

```text
copy_options::overwrite_existing
```

Therefore existing destination files are overwritten.

The Windows and Unix implementations also use copy mechanisms intended to replace the destination.

---

# 🪟 Windows Copying

When:

```text
CPP20
```

is not defined and the platform is Windows, Crossbow uses:

```text
CopyFileA()
```

with overwrite enabled.

A Win32 error code is logged if copying fails.

---

# 🐧 Non-Windows Copying

On non-Windows platforms, the fallback implementation executes:

```text
cp "<source>" "<destination>"
```

through:

```text
Common::executeBatch()
```

A non-zero return code marks the overall operation as unsuccessful.

---

# 🧱 C++20 Copying

When:

```text
CPP20
```

is defined, Crossbow uses:

```text
std::filesystem::copy_file()
```

with:

```text
overwrite_existing
```

If an exception occurs, it is logged.

---

# 📊 `allCopied`

Crossbow tracks whether all copy operations succeeded using:

```cpp
bool allCopied = true;
```

Each failure can change it to:

```text
false
```

At the end:

```text
allCopied == true
```

produces a success message.

Otherwise it reports:

```text
Some files failed to copy.
Check the log for details.
```

---

# 📄 `file_copied.txt`

After processing the modified list, Crossbow appends each selected file to:

```text
file_copied.txt
```

The file is opened with:

```text
std::ios::app
```

so previous contents are preserved.

---

# ⚠️ `file_copied.txt` Is Append-Only

Crossbow does not clear this file before writing.

Therefore it can contain entries from multiple Crossbow runs.

It should be treated as a historical log rather than a guaranteed representation of only the current run.

---

# ✂️ Shortened Paths in `file_copied.txt`

Crossbow writes:

```text
Common::ShortenFilename(j, 2)
```

rather than the complete original path.

Therefore the output is intended to be a compact record rather than a fully qualified source path.

---

# 🧹 Part 2 Cleanup

After Part 2 copying completes, Crossbow performs a cleanup operation:

```text
Removing leftovers
```

It examines:

```text
Distribute/
```

and removes leftover **files**.

---

# ⚠️ Part 2 Cleanup Does Not Recursively Delete Directories

The cleanup uses:

```text
std::filesystem::directory_iterator(actualdist)
```

and skips directories.

Therefore only top-level files in:

```text
Distribute/
```

are removed.

Existing subdirectories are not recursively deleted by this cleanup block.

---

# 🧹 Why Part 2 Cleans Leftovers

The intent is to ensure that the Part 2 distribution set contains only the current output.

Conceptually:

```text
Old Distribute/
    ├── old_file.spc
    ├── current_file.spc
    └── another_old_file.pb

        ↓ Crossbow Part2

New distribution set
    └── current resources
```

This helps prevent stale files from accidentally being packaged.

---

# ⚠️ Cleanup Timing

Cleanup occurs only when:

```text
part2 == true
```

and:

```text
modified is not empty
```

Therefore, an empty modified list does not trigger the cleanup block.

---

# 🔍 File Existence Handling

Before copying, Crossbow checks:

```text
std::filesystem::exists(f)
```

If the source does not exist, it logs:

```text
File does not exist
```

and skips the file.

It does not terminate the entire run.

---

# 🔁 Same-File Protection

Crossbow checks whether the source and destination are already the same filesystem object.

If:

```text
std::filesystem::equivalent(f, dest)
```

is true, it skips the copy.

This prevents an unnecessary self-copy operation.

---

# ⚠️ Important Path Behavior

The destination is normally different from the source because:

```text
source:
DGRV3/base_spc/

destination:
ModifiedFiles/
```

or:

```text
Distribute/
```

However, the equivalence check provides protection against unusual directory layouts or accidental self-targeting.

---

# 🧪 Normal Mode Example

Suppose:

```text
different_hashes.txt
```

contains a changed file belonging to:

```text
chapter3
```

and:

```text
DGRV3/base_spc/
```

contains:

```text
chap3_text_US.SPC
chap4_text_US.SPC
game_resident_US.spc
```

Crossbow recognizes:

```text
chap3_text_US.SPC
```

as belonging to:

```text
chapter3
```

and copies it to:

```text
ModifiedFiles/wrd_script/007/chap3_text_US.SPC
```

The chapter is then removed from `logged`.

---

# 🧪 PB Example

If:

```text
DGRV3/base_spc/
```

contains:

```text
something.pb
```

the PB file is considered modified automatically.

It is copied to:

```text
ModifiedFiles/master/something.pb
```

even if no chapter corresponding to it exists in `logged`.

---

# 🧪 Game Resident Example

A modified:

```text
game_resident_US.spc
```

is classified as:

```text
game_resident
```

and becomes:

```text
ModifiedFiles/game_resident/game_resident_US.spc
```

---

# 🧪 Map Object Example

A modified:

```text
map_obj_name_text_US.spc
```

becomes:

```text
ModifiedFiles/wrd_data/map_obj_name_text_US.spc
```

---

# 🧪 Trial Example

In Part 2, Crossbow explicitly adds:

```text
hanron_01_FR.spc
```

It recognizes this as a trial file and converts the name:

```text
hanron_01_FR.spc
        ↓
hanron_01_US.spc
```

The destination becomes:

```text
ModifiedFiles/wrd_data/hanron_01_US.spc
```

---

# 🚦 Failure Handling

Crossbow terminates with `-1` if:

```text
DGRV3/
```

does not exist.

It also terminates with `-1` if:

```text
DGRV3/base_spc/
```

does not exist.

Most other failures are non-fatal:

* missing `different_hashes.txt`,
* missing individual source files,
* copy errors,
* existing destination files,
* unsupported file types.

These are logged and the program continues.

---

# 🛑 Repository Validation

Crossbow requires:

```text
DGRV3/
DGRV3/base_spc/
```

before it can operate.

The source constructs these paths relative to:

```text
std::filesystem::current_path()
```

Therefore Crossbow expects to be launched from the appropriate TextTools working directory.

---

# 🧭 Current Working Directory Matters

Crossbow uses the current working directory for:

```text
DGRV3/
ModifiedFiles/
Distribute/
different_hashes.txt
file_copied.txt
```

Therefore launching the executable from an unrelated directory can cause it to report missing repository files.

# 🧩 Two-Part Architecture

Crossbow is best understood as having two logical parts.

```text
┌─────────────────────────────────────┐
│          Crossbow Part 1            │
│                                     │
│ DGRV3/base_spc/                     │
│       ↓                             │
│ modified SPC/PB detection           │
│       ↓                             │
│ ModifiedFiles/                      │
└─────────────────────────────────────┘

                 +

┌─────────────────────────────────────┐
│          Crossbow Part 2            │
│                                     │
│ Distribute/                         │
│       ↓                             │
│ top-level distribution files        │
│       +                             │
│ French trial resources              │
│       ↓                             │
│ Distribute/ + ModifiedFiles/wrd_data│
└─────────────────────────────────────┘
```

The two modes share the same executable and core copy/classification logic but operate on different source directories and have different trial behavior.

---

# 🔗 Crossbow Part 1 vs Part 2

| Behavior              | Normal            | `part2`                       |
| --------------------- | ----------------- | ----------------------------- |
| Source                | `DGRV3/base_spc/` | `Distribute/`                 |
| Main destination      | `ModifiedFiles/`  | `Distribute/`                 |
| Recursive scan        | Yes               | Top-level only                |
| PB files              | Always selected   | Selected if present in source |
| Trial files           | Normally skipped  | Explicitly added              |
| French trial handling | No                | Yes                           |
| FR → US rename        | No                | Yes                           |
| Cleanup               | No                | Yes                           |
| Game revision         | `007`             | `007`                         |

# 🧠 Why Part 2 Uses `Distribute/`

Part 2 is not simply another scan of `DGRV3/base_spc/`.

It assumes that an intermediate distribution set already exists in:

```text
Distribute/
```

Crossbow then uses that directory as its input while applying additional packaging rules.

This makes Part 2 a secondary distribution pass rather than a direct replacement for normal mode.

---

# 🔄 End-to-End Normal Workflow

The normal workflow can be represented as:

```text
1. Necronomicon detects changes
              │
              ▼
2. different_hashes.txt
              │
              ▼
3. Crossbow reads changed chapters
              │
              ▼
4. Scan DGRV3/base_spc/
              │
              ▼
5. Select changed SPCs + all PBs
              │
              ▼
6. Classify each resource
              │
              ├── game_resident
              ├── wrd_data
              ├── wrd_script/007
              └── master
              │
              ▼
7. Copy into ModifiedFiles/
              │
              ▼
8. Append entries to file_copied.txt
```

# 🔄 End-to-End Part 2 Workflow

Part 2 behaves more like:

```text
1. Start with Distribute/
              │
              ▼
2. Scan top-level SPC/PB files
              │
              ▼
3. Select eligible resources
              │
              ▼
4. Add mandatory French trial SPCs
              │
              ▼
5. Classify files
              │
              ▼

              │
              ▼

              │
              ▼
8. Place trial files in ModifiedFiles/wrd_data/
              │
              ▼

              │
              ▼
10. Remove leftover top-level files
```

# ⚠️ Important Developer Quirks

## 1. `logged` is consumed

A chapter disappears from `logged` after its first successful filename match.

---

## 2. PB files bypass chapter filtering

Every PB file is considered modified.

---

## 3. Only 12 chapter/resource mappings exist

Crossbow's mapping is smaller than ElectroHammer's complete folder list.

---

## 4. Game revision is hardcoded

The target revision is:

```text
007
```

---

## 5. Trial resources are special-cased

They are recognized using filename substring checks rather than a formal metadata system.

---

## 6. Part 2 explicitly injects trial files

The trial list is hardcoded into the source.

Adding a new trial resource requires a source change.

---

## 7. FR → US replacement is broad

The regex replaces every occurrence of:

```text
FR
```

in the filename.

---

## 8. `file_copied.txt` is persistent

It is opened in append mode and is not reset automatically.

---

## 9. Part 2 cleanup only removes top-level files

Subdirectories in `Distribute/` survive the cleanup pass.

---

## 10. Missing hashes do not abort execution

Crossbow continues even when:

```text
different_hashes.txt
```

cannot be opened.

# 🛠️ Developer Notes

### Adding a new chapter

A new chapter/resource mapping requires an entry in:

```cpp
chapters
```

For example:

```cpp
{ "chap8", "chapter8" }
```

Without this, `LoadLoggedFromFile()` and `ShouldBeSaved()` cannot associate the new SPC with a changed chapter.

---

### Changing the game revision

Modify:

```cpp
static const std::string latest_game_revision = "007";
```

The resulting distribution path will change from:

```text
wrd_script/007/
```

to the new revision.

---

### Adding a new trial resource

Part 2 trial files are explicitly listed in `main()`.

A new resource therefore requires another:

```cpp
modified.push_back(...)
```

entry.

It may also require updates to:

```text
is_trial_file
```

so that the destination logic recognizes it as a trial.

---

### Changing distribution folders

The destination classification is encoded directly in the `filepath` expression.

Changes to the packaging structure therefore require source modifications.

# 🏁 Summary

Crossbow is the **final distribution and packaging-selection tool in TextTools**.

Its job is not to compile scripts or modify SPC contents.

Instead, it answers:

> **Which already-built game resources should be distributed?**

It uses Necronomicon's:

```text
different_hashes.txt
```

to identify changed chapters, scans the relevant SPC/PB resources, and copies only the necessary files.

The normal workflow is:

```text
different_hashes.txt
        ↓
changed chapters
        ↓
DGRV3/base_spc/
        ↓
modified SPC/PB selection
        ↓
resource classification
        ↓
ModifiedFiles/
```

Part 2 adds a specialized distribution workflow:

```text
Distribute/
    +
French trial SPCs
    ↓
special trial handling
    ↓
FR → US renaming
    ↓
final distribution set
```

Crossbow therefore acts as the **bridge between the compiled TextTools output and the files intended for packaging, testing, or release**.

In short:

```text
Necronomicon
    ↓
"What changed?"
    
ElectroHammer
    ↓
"Build the changed game resources."

Crossbow
    ↓
"Distribute only the resources that need to ship."
```
