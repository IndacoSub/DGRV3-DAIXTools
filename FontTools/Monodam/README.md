# FONTTOOLS - MONODAM
# Team DAIX, 2026

---

## 📌 Overview

**Monodam** is the font compilation stage of the **FontTools** pipeline.

Its purpose is to take the prepared font directories produced earlier in the FontTools workflow, compile those directories into the game's required **STX/SRDV** font resources using the legacy **HTFont** utility, and then insert those resources into the appropriate **SPC archives** using **SpcTool**.

At a high level:

```text
Prepared font directory
        │
        ▼
      HTFont
        │
        ├── .srd
        └── .srdv
        │
        ▼
    .srd → .stx
        │
        ├── .stx ──┐
        │          │
        └── .srdv ┤
                   ▼
                SpcTool
                   │
                   ▼
              target .spc
````

Monodam therefore sits between **font preparation** and **SPC filtering/patch generation**.

It is not responsible for creating the prepared font data itself. Instead, it takes the prepared data and turns it into the binary resources that the game actually consumes.



---

# 🎯 Responsibilities

Monodam performs several distinct jobs during a run.

### 1. Locate the DGRV3-Font repository

Monodam expects a repository named:

```text
DGRV3-Font
```

in the current working directory.

It then uses:

```text
DGRV3-Font/base_spc
```

as the main working area for its tools and base SPC resources.

---

### 2. Remove temporary files

Before processing fonts, Monodam recursively scans the repository and removes files whose paths contain:

```text
.bat
```

or:

```text
charset.txt
```

These files are considered leftovers that should not remain in the prepared font tree when HTFont is executed.

---

### 3. Discover prepared font directories

Monodam recursively searches the repository for directories matching the expected structure:

```text
*_DEC/v3_fontXX/
```

These directories are assumed to contain the prepared font data generated by the preceding **Monophanie** stage.

---

### 4. Provide HTFont with its runtime dependency

HTFont requires:

```text
Windows:
    assimp.dll

Linux:
    libassimp.so
```

Monodam copies the dependency into the directory in which HTFont will execute.

---

### 5. Copy HTFont into each font directory

Monodam also copies:

```text
HTFont.exe
```

or:

```text
HTFont
```

into the appropriate font directory before invoking it.

This is intentional: HTFont is expected to run from the directory containing the font data it is packing.

---

### 6. Compile the font

Monodam executes:

```text
HTFont --pack <font_folder>
```

HTFont produces:

```text
<font>.srd
<font>.srdv
```

---

### 7. Convert `.srd` into `.stx`

HTFont creates an `.srd` file, but the game expects the corresponding resource to use the `.stx` extension.

Monodam therefore renames:

```text
<font>.srd
```

to:

```text
<font>.stx
```

The `.srdv` file is retained without modification.

---

### 8. Locate the correct SPC

Monodam calculates the font folder's relative path within `DGRV3-Font` and uses that path to determine which SPC archive inside:

```text
base_spc/base_fonts/
```

should receive the compiled font.

---

### 9. Insert the compiled resources

For the target SPC, Monodam invokes **SpcTool** twice:

```text
SpcTool <spc> <stx>
SpcTool <spc> <srdv>
```

on Windows, with the platform-specific command syntax used by the source.

The result is a modified SPC containing both resources.

---

### 10. Record modified SPCs

Every successfully targeted SPC is added to:

```text
list_changed.txt
```

This list is consumed by later stages of FontTools.



---

# 🧩 How Monodam Fits Into FontTools

Monodam is not the first stage of FontTools.

The intended flow is:

```text
Monokuma
    │
    ▼
Monotaro
    │
    ▼
DGRV3-Font repository
    │
    ▼
Monophanie
    │
    ▼
Prepared font folders
    │
    ▼
Monodam
    │
    ▼
Compiled STX/SRDV
    │
    ▼
Modified SPCs
    │
    ▼
Monokid
    │
    ▼
Monosuke
```

The old README identifies Monodam as stage **3** of this pipeline:

```text
0. Monokuma — orchestrator
1. Monotaro — clone/update repository
2. Monophanie — prepare font folders
3. Monodam — compile fonts
4. Monokid — filter SPCs
5. Monosuke — generate UPS patches
```



The source code specifically assumes that the repository has already been cloned and that the font directories have already been prepared.

---

# 🏗️ Pipeline Relationship

The most important distinction is:

```text
Monophanie
    ↓
prepares font data
```

whereas:

```text
Monodam
    ↓
compiles prepared font data
```

Monodam therefore should not be treated as a font-authoring or font-preparation tool.

Its input is already-prepared data.

---

# 📁 Expected Repository

The effective repository root is:

```text
DGRV3-Font/
```

Monodam expects:

```text
DGRV3-Font/
├── base_spc/
│   ├── HTFont.exe / HTFont
│   ├── SpcTool.exe / SpcTool
│   ├── assimp.dll / libassimp.so
│   └── base_fonts/
│       └── ...
│
├── *_DEC/
│   └── v3_fontXX/
│       └── prepared font data
│
└── ...
```

The exact font-directory names are not hard-coded.

Instead, Monodam searches recursively for directories whose paths contain the required `_DEC` and `v3_` components.

---

# 📂 Repository Detection

Monodam establishes:

```cpp
repo = EncryptString("DGRV3-Font");
```

and then:

```text
current working directory
        │
        ▼
DGRV3-Font/
```

The base working directory is:

```text
DGRV3-Font/base_spc/
```

If this directory does not exist, Monodam immediately logs:

```text
ERROR: The folder where the files to copy are located was not found!
```

and terminates with:

```text
-1
```



---

# 📥 Inputs

Monodam's main inputs are:

| Input                         | Purpose                                   |
| ----------------------------- | ----------------------------------------- |
| `DGRV3-Font/`                 | Main font repository                      |
| `base_spc/`                   | Tool/dependency and SPC working directory |
| `base_fonts/`                 | Original font SPC archives                |
| `*_DEC/v3_fontXX/`            | Prepared font data                        |
| `HTFont` / `HTFont.exe`       | Font compiler                             |
| `assimp.dll` / `libassimp.so` | HTFont dependency                         |
| `SpcTool`                     | SPC modification utility                  |

The actual contents of each `v3_fontXX` directory are consumed by HTFont rather than interpreted by Monodam itself.

---

# 🧹 Cleanup Stage

Before locating font folders, Monodam recursively walks:

```text
DGRV3-Font/
```

and builds a deletion list.

It searches every non-directory entry for:

```text
.bat
```

and:

```text
charset.txt
```

Any matching path is added to:

```cpp
todelete
```

and subsequently removed.



---

# ⚠️ Cleanup Uses Substring Matching

This is an important implementation detail.

The code does not check that a file's extension is **exactly** `.bat`.

It checks whether the complete path contains:

```text
.bat
```

Likewise, `charset.txt` is detected through substring matching.

Therefore the behavior is broader than a strict:

```text
extension == ".bat"
```

test.

Developers should be aware of this if unusual filenames are introduced into the repository.

---

# ⚠️ Cleanup Is Destructive

The matching files are physically deleted:

```cpp
std::filesystem::remove(td);
```

There is no backup step.

Therefore the cleanup phase should be treated as destructive repository preparation.

---

# 🔎 Font Directory Discovery

After cleanup, Monodam recursively walks the repository again.

A directory is considered a font candidate only if:

1. its path does **not** contain `base_spc`,
2. its path contains `_DEC`,
3. its path contains `v3_`,
4. it is actually a directory.

The source comments describe the intended form as:

```text
something_DEC/v3_fontXX/
```



---

# 🧠 Detection Is Pattern-Based

Monodam does not maintain a hard-coded list such as:

```text
v3_font00
v3_font01
v3_font02
...
```

Instead, it discovers directories by path contents.

That makes the compiler flexible enough to process additional matching font directories without modifying the source.

However, it also means the detection logic is relatively permissive.

For example, the code checks for the presence of `_DEC` and `v3_`; it does not use a formal regular expression to verify the exact:

```text
*_DEC/v3_fontXX/
```

pattern.

---

# 📁 Understanding `cur_folder`

For every discovered font directory:

```cpp
cur_folder = file.path();
```

The source then stores:

```cpp
program_folder = cur_folder.parent_path();
```

If the structure is:

```text
trial_font/
└── something_DEC/
    └── v3_font01/
```

then:

```text
cur_folder
    = .../something_DEC/v3_font01

program_folder
    = .../something_DEC
```

This distinction is important because the generated `.stx` and `.srdv` are expected in the **parent directory**, not inside the `v3_fontXX` directory.

---

# 📦 HTFont Deployment

For every font variant, Monodam copies:

```text
base_spc/HTFont(.exe)
```

to:

```text
<program_folder>/HTFont(.exe)
```

It also copies:

```text
base_spc/assimp.dll
```

or:

```text
base_spc/libassimp.so
```

to the same program directory when the dependency exists.



---

# 🧩 Why HTFont Is Copied

The source explicitly notes that HTFont:

> must run inside the folder it is packing

The compiler therefore does not simply execute a single global HTFont binary against arbitrary paths.

Instead, it creates a local execution environment for each prepared font directory.

Conceptually:

```text
base_spc/
└── HTFont

        │ copy

        ▼

font_group/
├── HTFont
├── assimp.dll
└── v3_fontXX/
```

HTFont is then executed from that context.

---

# 🔧 HTFont

HTFont is the actual font packing engine.

Monodam invokes it as:

```text
HTFont --pack <font_folder>
```

For Windows the command is quoted:

```text
"HTFont.exe" --pack <font_folder>
```

For non-Windows systems:

```text
HTFont --pack <font_folder>
```



---

# 🧠 What HTFont Produces

Monodam expects HTFont to generate:

```text
<font>.srd
<font>.srdv
```

The source comments describe these as the generated font resources.

Monodam does not parse their internal binary structures.

It simply takes the resulting files and prepares them for insertion into the game's SPC archive.

---

# 🔄 `.srd` → `.stx`

One of the most important quirks in Monodam is that HTFont's output extension does not match the game's expected extension.

HTFont produces:

```text
font.srd
```

but the game expects:

```text
font.stx
```

Monodam therefore performs:

```text
font.srd
   │
   ▼
font.stx
```

using a filesystem move/rename operation.

The `.srdv` file remains:

```text
font.srdv
```



---

# ⚠️ `.srd` Is Not Recompiled

Monodam does not transform the binary contents of the `.srd`.

The conversion is effectively a filename/extension change:

```text
.srd → .stx
```

The source explicitly describes this as:

```text
".srd is .stx"
```

Therefore the important distinction is the **filename expected by the game**, not a different binary compilation format.

---

# 🗑️ Existing `.stx`

Before renaming the newly generated `.srd`, Monodam checks whether:

```text
<font>.stx
```

already exists.

If it does, the existing `.stx` is deleted first.

Only after that does Monodam perform the `.srd` → `.stx` move.

This prevents the old file from blocking the replacement.



---

# 🧹 HTFont Cleanup

After packing, Monodam removes the temporary copied:

```text
HTFont
```

and:

```text
assimp.dll
```

or:

```text
libassimp.so
```

from the program directory.

This keeps the font tree from accumulating copies of the compiler and its dependency.

---

# ⚠️ Dependency Cleanup Is Conditional

The dependency is only removed if Monodam found/copied it in the first place.

Therefore:

```text
base_spc/assimp.dll
```

is not required to exist for the cleanup branch itself to execute.

However, HTFont may still require the dependency to successfully perform its work.

---

# 🛑 `game_resident` Special Case

After generating the `.stx` and `.srdv`, Monodam checks whether the discovered path contains:

```text
game_resident
```

If it does, the function immediately continues to the next discovered font directory.

This means the font still goes through:

```text
HTFont
→ .srd
→ .stx
```

but it does **not** proceed through the normal SPC lookup/insertion stage.



---

# 🧩 Why `game_resident` Is Special

The source does not provide a deeper explanation for this exception.

What can be established from the implementation is:

```text
game_resident
    ↓
compile font
    ↓
skip SPC mapping/insertion
```

Therefore developers should not assume that every generated STX/SRDV will be inserted into an SPC by Monodam.

`game_resident` is an explicit exception.

---

# 🗺️ Mapping a Font to Its SPC

For normal fonts, Monodam needs to determine which SPC contains the font.

It calculates:

```cpp
std::filesystem::relative(program_folder, dgrv3path)
```

This produces the font's location relative to:

```text
DGRV3-Font/
```

For example, conceptually:

```text
DGRV3-Font/
└── trial_font/
    └── chapter1_DEC/
        └── v3_font01/
```

may produce a relative program path resembling:

```text
trial_font/chapter1_DEC
```

The exact path depends on the repository structure.

---

# 📁 `base_fonts`

The target SPC directory is:

```text
DGRV3-Font/base_spc/base_fonts/
```

Monodam combines this directory with the relative font path.

Conceptually:

```text
relative font path
        │
        ▼
base_spc/base_fonts/
        │
        ▼
candidate SPC path
```

---

# ✂️ Removing `_DEC`

The source then removes the suffix:

```text
_DEC
```

from the generated path.

This is how the prepared directory naming convention is mapped back to the name of the corresponding original SPC.

For example:

```text
something_DEC
```

becomes:

```text
something
```

before the `.spc` extension is considered.

---

# 📦 SPC Extension Handling

Monodam checks both:

```text
.spc
```

and:

```text
.SPC
```

If the lowercase version exists, it uses:

```text
.spc
```

otherwise it falls back to:

```text
.SPC
```

This gives the compiler some tolerance for repositories whose original archive capitalization differs.



---

# ⚠️ Missing SPC Behavior

If the calculated SPC does not exist, Monodam logs:

```text
WARNING: SPC does not exist: <path>
```

and skips that font.

It does **not** terminate the entire compilation process.

The remaining discovered fonts continue to be processed.

This is an important difference from the initial `base_spc` validation, which is fatal.

---

# 🧩 SPC Mapping Summary

The mapping logic can be summarized as:

```text
Prepared font path
        │
        ▼
Find program_folder
        │
        ▼
Make path relative to DGRV3-Font
        │
        ▼
Append to:
base_spc/base_fonts/
        │
        ▼
Remove "_DEC"
        │
        ▼
Try ".spc"
        │
        └── if missing → try ".SPC"
        │
        ▼
Target SPC
```

---

# 🛠️ SpcTool Integration

Once the target SPC has been located, Monodam invokes **SpcTool**.

The SpcTool executable is expected at:

```text
<current working directory>/SpcTool(.exe)
```

This is distinct from the HTFont location.

The source constructs:

```cpp
spctool_loc = current_dir / ("SpcTool" + ext);
```



---

# 📥 STX Insertion

Monodam passes the target SPC and generated `.stx` to SpcTool.

On Windows the source constructs:

```text
"SpcTool.exe" <spc> <stx>
```

On non-Windows systems it explicitly uses:

```text
SpcTool <spc> insert <stx>
```

The platform-specific command syntax is therefore not identical.

---

# 📥 SRDV Insertion

The `.srdv` file is inserted separately.

Conceptually:

```text
SpcTool
    │
    ├── insert STX
    │
    └── insert SRDV
```

The resulting SPC therefore receives both pieces of the compiled font resource.

---

# 🔄 Complete Per-Font Process

For one discovered font directory, Monodam effectively performs:

```text
Find *_DEC/v3_fontXX/
        │
        ▼
Copy HTFont
        │
        ▼
Copy assimp dependency
        │
        ▼
HTFont --pack <font_folder>
        │
        ├── font.srd
        └── font.srdv
        │
        ▼
Delete old font.stx
        │
        ▼
Rename font.srd → font.stx
        │
        ▼
Delete temporary HTFont/dependency
        │
        ▼
game_resident?
    │          │
   YES         NO
    │           │
    ▼           ▼
  skip      calculate SPC
                │
                ▼
          find .spc/.SPC
                │
                ▼
          SpcTool + STX
                │
                ▼
          SpcTool + SRDV
                │
                ▼
          record SPC
```

---

# 📤 Outputs

Monodam produces several kinds of output.

## Compiled font resources

For each processed font:

```text
<font>.stx
<font>.srdv
```

These are generated next to the prepared font directory's parent folder.

---

## Modified SPC archives

The corresponding archive under:

```text
base_spc/base_fonts/
```

is modified by SpcTool.

The SPC contains the inserted:

```text
.stx
.srdv
```

resources.

---

## `list_changed.txt`

Monodam appends the shortened name of every targeted SPC to:

```text
list_changed.txt
```

This file is opened with:

```cpp
std::ios::app
```

so existing contents are preserved and new entries are appended.



---

# 📝 `list_changed.txt`

The purpose of this file is to provide downstream tools with a record of which SPC archives were modified.

For each processed SPC:

```text
spc_str
```

is added to:

```cpp
list_changed
```

At the end of execution, each path is passed through:

```cpp
Common::ShortenFilename(entry, 3)
```

before being written to the file.

---

# ⚠️ `list_changed.txt` Is Append-Only

Monodam does not truncate:

```text
list_changed.txt
```

when it starts.

Instead:

```cpp
std::ofstream out("list_changed.txt", std::ios::out | std::ios::app);
```

means new results are appended to existing results.

Therefore an old `list_changed.txt` can contain entries from previous runs.

Downstream tooling should account for this if it expects the file to represent **only the current run**.

---

# 🧰 HTFont Dependency

HTFont comes from the **older Harmony-Tools** toolset.

The source comments identify it as an older component of Harmony-Tools and explain that the modern Harmony-Tools project has since been consolidated into a unified executable.

Monodam nevertheless continues to use the older HTFont component because the existing FontTools pipeline depends on its behavior.



---

# 🧠 Why Monodam Uses Legacy HTFont

The source identifies several reasons for retaining the legacy tool:

* stable STX/SRDV packing behavior,
* compatibility with the existing DAIXTOOLS font pipeline,
* compatibility with existing SPC workflows.

The old README additionally describes the workflow as deterministic and reproducible.

The important practical point is that replacing HTFont with a different font compiler is **not automatically equivalent**.

The exact generated resource structure needs to remain compatible with the game's expected font/SPC format.

---

# 🔧 Why Monodam Does Not Use Modern Harmony-Tools

Modern Harmony-Tools may provide a unified executable, but Monodam's source is specifically structured around:

```text
HTFont
```

and its:

```text
--pack
```

operation.

Changing this dependency would therefore be a pipeline-level change, not merely a filename substitution.

---

# 🖥️ Platform Support

Monodam contains explicit platform handling for:

```text
Windows
Linux / non-Windows
```

The main differences are:

| Component       | Windows       | Non-Windows    |
| --------------- | ------------- | -------------- |
| HTFont          | `HTFont.exe`  | `HTFont`       |
| Assimp          | `assimp.dll`  | `libassimp.so` |
| SpcTool         | `SpcTool.exe` | `SpcTool`      |
| `.srd` → `.stx` | `MoveFileA`   | `mv`           |
| cleanup         | Win32 APIs    | shell commands |

The source selects the executable extension through:

```cpp
#ifdef _WIN32
```



---

# 🪟 Windows Behavior

On Windows, Monodam uses:

```cpp
MoveFileA()
```

to rename:

```text
.srd → .stx
```

and:

```cpp
DeleteFileA()
```

to remove temporary files.

HTFont and SpcTool are also treated as:

```text
.exe
```

executables.

---

# 🐧 Non-Windows Behavior

On non-Windows systems, Monodam uses shell commands through:

```cpp
Common::executeBatch()
```

for operations such as:

```text
mv
rm
```

The source expects:

```text
HTFont
SpcTool
libassimp.so
```

without Windows executable extensions.

---

# ⚠️ Shell Command Considerations

Because the non-Windows implementation constructs commands as strings and passes them to:

```cpp
Common::executeBatch()
```

paths containing unusual shell characters may be more fragile than ordinary filesystem API operations.

This is particularly relevant for:

```text
mv
rm
```

operations.

The source does not implement comprehensive shell escaping around these paths.

---

# ⚙️ No Multithreading

Monodam processes discovered font folders sequentially.

There is no thread pool or worker-thread mechanism in the source.

The effective model is:

```text
Font 1
  ↓
HTFont
  ↓
SPC insertion
  ↓
Font 2
  ↓
HTFont
  ↓
SPC insertion
  ↓
...
```

Therefore total execution time grows with the number of fonts and the cost of HTFont packing and SPC rewriting.

---

# 📈 Performance Characteristics

The expensive operations are:

### HTFont packing

```text
prepared font
    ↓
HTFont
    ↓
STX/SRDV
```

### SPC insertion

```text
STX/SRDV
    ↓
SpcTool
    ↓
repacked SPC
```

Because both stages are executed sequentially for each discovered font, large font sets can take significant time.

The old README describes Monodam as potentially taking several minutes for large font sets.



---

# ⚠️ Existing SPCs Are Modified In Place

Monodam does not create a separate output SPC for every font.

Instead, SpcTool is given the existing archive path:

```text
<target>.spc
```

and inserts the generated resources directly into it.

Therefore the original base SPC is modified.

Developers should ensure that untouched originals are preserved elsewhere if rollback is required.

---

# ⚠️ Existing STX Is Deleted

Similarly, an existing:

```text
<font>.stx
```

is explicitly deleted before the new `.stx` is created.

This means Monodam treats the generated resource as authoritative for the current compilation run.

---

# 🧪 Failure and Warning Behavior

Monodam has several different classes of failure.

## Missing `base_spc`

Fatal:

```text
ERROR: The folder where the files to copy are located was not found!
```

The program returns:

```text
-1
```

---

## Missing target SPC

Non-fatal:

```text
WARNING: SPC does not exist: ...
```

The font is skipped and processing continues.

---

## Missing HTFont

The source does not explicitly perform a dedicated `exists()` validation before copying HTFont.

Therefore failure is likely to occur through the filesystem copy operation.

---

## Missing Assimp dependency

The source only copies the dependency if:

```cpp
std::filesystem::exists(libassimp_before)
```

is true.

It does not explicitly abort if the dependency is absent.

HTFont may subsequently fail if it actually requires the library.

---

# ⚠️ HTFont Exit Status

Monodam invokes HTFont through:

```cpp
Common::executeBatch()
```

but the source shown does not explicitly inspect a returned process exit code before continuing.

Therefore Monodam does not independently validate that HTFont successfully generated:

```text
.srd
.srdv
```

before proceeding with the subsequent filesystem operations.

The presence or absence of those generated files determines what happens next.

---

# ⚠️ Missing `.srd`

If HTFont fails to create the expected:

```text
<font>.srd
```

the subsequent `.srd` → `.stx` operation cannot produce the expected output.

The source does not contain a dedicated error message such as:

```text
HTFont compilation failed
```

for this case.

Developers should therefore inspect HTFont's output/logging and the generated files when diagnosing compilation failures.

---

# ⚠️ Missing `.srdv`

The source similarly expects:

```text
<font>.srdv
```

to exist after HTFont runs.

There is no explicit pre-insertion existence check before SpcTool is invoked.

A missing `.srdv` therefore becomes a downstream SpcTool/file-handling problem.

---

# 🧪 Missing `base_fonts`

The initial validation only checks:

```text
DGRV3-Font/base_spc
```

It does not explicitly validate:

```text
DGRV3-Font/base_spc/base_fonts
```

before processing.

The actual SPC lookup will fail later if `base_fonts` does not contain the expected archive.

---

# 🧭 Directory Matching Caveat

The source uses:

```cpp
Common::StringContains(file_str, "_DEC")
```

and:

```cpp
Common::StringContains(file_str, "v3_")
```

rather than checking exact directory names.

This means Monodam's scanner is based on **path substring matching**.

A directory can therefore qualify because its complete path happens to contain those strings, even if its exact structure is not the intended:

```text
*_DEC/v3_fontXX/
```

form.

---

# 🧩 Why the `base_spc` Check Exists

The font discovery loop explicitly ignores paths containing:

```text
base_spc
```

This prevents Monodam from treating the base SPC/tool directory as a prepared font source.

Without this exclusion, recursive scanning could encounter unrelated directories that happen to satisfy the other path tests.

---

# 🗃️ Font Output Location

The generated:

```text
.stx
.srdv
```

files are placed in:

```text
program_folder
```

which is the parent directory of the discovered:

```text
v3_fontXX
```

directory.

Therefore the compiled files do not remain inside the `v3_fontXX` folder itself.

---

# 🔄 Example Directory Transformation

A conceptual input:

```text
DGRV3-Font/
└── trial_font/
    └── chapter1_DEC/
        └── v3_font01/
            ├── ...
            └── font data
```

may become:

```text
DGRV3-Font/
└── trial_font/
    └── chapter1_DEC/
        ├── font01.stx
        ├── font01.srdv
        └── v3_font01/
            └── ...
```

The exact generated filename is determined by the directory name HTFont operates on.

---

# 📦 Example SPC Mapping

The corresponding path is then mapped into:

```text
DGRV3-Font/
└── base_spc/
    └── base_fonts/
        └── ...
```

The `_DEC` suffix is removed from the calculated path before the archive extension is appended.

Thus the prepared-directory naming convention acts as a bridge between:

```text
prepared font data
```

and:

```text
original game SPC
```

---

# 🔁 One Font Can Modify One SPC

The intended model is essentially:

```text
font preparation directory
        │
        ▼
one generated STX
one generated SRDV
        │
        ▼
one corresponding SPC
```

Multiple font directories can of course map to different SPCs over the course of a complete run.

---

# 📝 Logging

Monodam uses the shared:

```cpp
LOG(...)
```

facility from:

```text
Common/Common.h
```

It logs operations including:

* missing base directories,
* copied HTFont binaries,
* copied Assimp dependencies,
* relative path calculations,
* missing SPCs,
* selected SPCs,
* entries added to `list_changed.txt`.

This makes the console output useful for diagnosing which stage of the per-font process is currently executing.

---

# 🧠 What Monodam Does Not Understand

Monodam does not parse the internal contents of:

```text
.stx
.srdv
.spc
```

It delegates their creation/manipulation to:

```text
HTFont
SpcTool
```

This is important architecturally.

Monodam is a **pipeline coordinator and file-routing layer**, not a binary font-format implementation.

---

# 🧰 External Tool Responsibilities

| Tool    | Monodam's use                                   |
| ------- | ----------------------------------------------- |
| HTFont  | Compile prepared font data into SRD/SRDV        |
| SpcTool | Insert STX/SRDV into SPC                        |
| assimp  | HTFont runtime dependency                       |
| Common  | Logging, command execution, path/string helpers |

Monodam coordinates these components rather than reimplementing their functionality.

# 🛠️ Developer Notes

### Preserve HTFont compatibility

Replacing HTFont with a different version should be treated as a compatibility-sensitive change.

The pipeline depends on the generated STX/SRDV being accepted by the existing game/SPC workflow.

---

### Preserve `_DEC` naming

The `_DEC` suffix is not merely cosmetic.

Monodam uses it when mapping prepared font directories back to the target SPC name.

Changing the naming convention without updating Monodam will break SPC discovery.

---

### Preserve `v3_` naming

Font directory discovery relies on the `v3_` substring.

Directories that no longer contain the expected naming convention may not be discovered.

---

### Preserve `base_fonts`

The target SPCs are resolved relative to:

```text
base_spc/base_fonts/
```

Moving that directory requires changes to the source.

---

### Be careful with `list_changed.txt`

Because the file is opened in append mode, stale entries can survive between runs.

For automated builds, consider clearing it at the appropriate pipeline stage if downstream tools expect a clean per-run list.

---

# ⚠️ Important Implementation Quirks

Monodam has several behaviors that developers should know about.

### 1. `.srd` is renamed, not converted

```text
.srd → .stx
```

is a filesystem rename.

---

### 2. `game_resident` skips SPC insertion

The font is compiled but not inserted through the normal SPC path.

---

### 3. Missing SPCs are warnings

A missing target archive does not abort the whole run.

---

### 4. `.spc` and `.SPC` are both supported

The lowercase form is preferred if both exist.

---

### 5. Temporary HTFont copies are removed

The compiler is copied into each working directory only for the duration of that font's compilation.

---

### 6. Cleanup is destructive

`.bat` and `charset.txt` files are deleted.

---

### 7. Processing is sequential

There is no multithreaded font compilation.

---

### 8. `list_changed.txt` is appended

Previous contents are not automatically cleared.

---

# 🚨 Reproducibility Considerations

Monodam is designed for repeatable automated builds, but reproducibility depends on several external factors:

* the exact HTFont version,
* the exact prepared font input,
* the exact base SPC archives,
* the exact SpcTool version,
* the same platform/runtime behavior,
* and consistent repository contents.

Because Monodam modifies SPCs in place, running against an already-modified base repository is not equivalent to running against untouched originals.

For reproducible builds, preserve clean base assets and perform compilation from a known state.

---

# 🧪 Recommended Build State

A clean run should conceptually begin with:

```text
Clean DGRV3-Font repository
        │
        ▼
Monophanie-prepared font directories
        │
        ▼
Untouched base SPC archives
        │
        ▼
Monodam
```

rather than repeatedly compiling against previously modified SPCs.

# 🧠 Design Philosophy

Monodam follows the same general philosophy as the rest of the DAIXTOOLS pipeline:

```text
Automate repetitive work
        +
Use deterministic naming
        +
Reuse established binary tools
        +
Produce machine-readable downstream output
```

Instead of manually compiling each font and manually inserting each result into its SPC, Monodam performs the entire repetitive sequence automatically.

The result is:

```text
prepared fonts
      ↓
automated compilation
      ↓
automated SPC mapping
      ↓
automated insertion
      ↓
automated change list
```

# 🏁 Summary

**Monodam is the FontTools font compiler.**

Its job is to take the prepared font directories produced by **Monophanie**, compile them with the legacy **HTFont** utility, rename HTFont's `.srd` output to the game's expected `.stx` extension, preserve the generated `.srdv`, locate the appropriate SPC archive, and insert both resources using **SpcTool**.

The complete process is:

```text
DGRV3-Font
    │
    ▼
Find *_DEC/v3_fontXX/
    │
    ▼
Remove temporary .bat / charset.txt files
    │
    ▼
Copy HTFont + Assimp dependency
    │
    ▼
HTFont --pack
    │
    ├── .srd
    └── .srdv
    │
    ▼
Rename .srd → .stx
    │
    ▼
Remove temporary HTFont/dependency
    │
    ▼
Resolve target SPC from relative path
    │
    ▼
SpcTool → insert .stx
    │
    ▼
SpcTool → insert .srdv
    │
    ▼
Record SPC in list_changed.txt
```

Its most important characteristics are:

* **HTFont-based** font compilation
* **STX/SRDV** generation
* `.srd` → `.stx` renaming
* automatic **SPC mapping**
* **SpcTool** integration
* Windows and Linux support
* automatic HTFont/dependency deployment
* cleanup of temporary font-build files
* special handling for `game_resident`
* `.spc` / `.SPC` compatibility
* sequential processing
* downstream change tracking through `list_changed.txt`

The key architectural relationship is:

```text
Monophanie
    │
    │ prepared font data
    ▼
Monodam
    │
    │ STX + SRDV
    ▼
SpcTool
    │
    │ modified SPC
    ▼
Monokid / Monosuke
```

In short:

> **Monophanie prepares the fonts. Monodam compiles them. SpcTool puts them into the game. Monokid and Monosuke take the resulting changes further down the pipeline.**
